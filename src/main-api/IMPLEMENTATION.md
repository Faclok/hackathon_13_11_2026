# Реализация школьного MVP ядра

14 ноября 2026. Источник требований — START-HERE.md и последующие уточнения пользователя.

## Окружение и зависимости

Установлены системные SDK .NET 10.0.404 и ASP.NET Core runtime 10.0.15. SDK закреплён в global.json. EF Core/Identity/OpenAPI/JWT — 10.0.15, Npgsql EF Core — 10.0.3; версии заданы в проектах, dotnet-ef — локальным manifest. Git инициализирован; исходные документы сохранены первым коммитом.

Граф: Domain ← Application ← Infrastructure ← Host. Domain не зависит от EF/ASP.NET. Application задаёт команды, результаты и интерфейсы сценариев; Infrastructure реализует их через EF Core, Identity и PostgreSQL. Никаких интерфейсов-репозиториев на каждую сущность нет.

## Принятые в этой сессии решения

- Администратор создаёт школы и назначает учителей. Учитель создаёт классы в своей школе и учеников своих классов. Каждый активный аккаунт может работать экспертом.
- Собственный issuer ядра выдаёт JWT HS256 с настраиваемыми issuer/audience/секретным ключом. Срок 15 минут. Каждый запрос проверяет активность аккаунта и SessionVersion в БД. Роли и доверие в JWT не передаются.
- Identity/Data Protection выдаёт токены установки/сброса пароля на 24 часа. Повторная выдача меняет SecurityStamp; успешная установка меняет stamp и SessionVersion, отзывая прежние ссылки и JWT. Отдельной таблицы ссылок нет. Ключи Data Protection сохраняются между запусками.
- Сервер возвращает accountId/token/expiresAt; внешний клиент строит из них персональную ссылку на собственную форму. Домен клиента пока не выбран. GET ничего не погашает, пароль меняет только POST `/auth/password`.
- Стартовые изменяемые настройки: N=300, порог 51%, минимум 2 школы/3 класса, доли 60%/40%, резервирование 30 минут, повтор через 24 часа, рабочий набор 20 случаев. Администратор создаёт новую версию; выдача хранит её ID. При недостатке аудитории нет автоматического ослабления квот.

## Что работает

Контролируемый bootstrap первого администратора; создание школ, учителей/поставщиков, классов и учеников; установка пароля и вход. Проверки permissions вместе с областью назначения выполняются в сценариях; принадлежность класса проверяется на сервере. Экспертные операции доступны каждому активному аккаунту. Создание ученика повторобезопасно по логину внутри того же класса.

Поставка одного элемента атомарна. Внешний producer берётся из аутентификации. Повтор ProducerId + Idempotency-Key возвращает прежний результат, изменённое содержимое даёт 409. Для многосоставных/частично принятых пакетов договор пока не утверждён; такого поведения здесь нет. Вход использует fragment_id/text_ba/lang_pair/translation/source. Существующий внешний фрагмент нельзя незаметно заменить новой версией.

Распределитель выбирает из рабочего набора активных случаев: меньшая представленность школы, затем класса, затем меньше повторов; при равенстве — возраст/ID. Учитываются ответы и живые резервы, пропуски освобождают резерв. Ограничение группы — floor(N × максимальная доля) уникальных участников с учётом резервов. Истечение снимает резерв. Повтор допустим через заданный интервал; уже активная выдача возвращается повторно. Участники без школы получают задания в общем потоке, с настоящими null в снимке школы/класса. Их принятия входят в N и процент. Охват и доли групп рассчитываются среди школьных участников: самостоятельные участники не создают группы и не разбавляют концентрацию одной школы. При недостатке охвата случай остаётся для эксперта.

Самостоятельная регистрация POST `/auth/register` требует только логин/пароль и создаёт обычного участника с собственными правами account/participant. Email и Telegram не обязательны. GET `/api/me` возвращает собственный профиль и nullable schoolId/classId. Регистрация ограничена по IP: 10 запросов за 60 секунд; Registration:PermitLimit/WindowSeconds настраиваются. Восстановление POST `/api/accounts/{id}/recovery-link` доступно администратору с accounts.credentials.reset после ручной проверки и требует verificationNote для аудита. Оно запрещено для школьных и привилегированных аккаунтов. Новая ссылка отменяет прежнюю, завершение восстановления через `/auth/password` отзывает access/refresh, сохраняя аккаунт и историю.

Ответ привязан к своей выдаче. Confirm поддерживает показанный вариант, Correct создаёт только положительное утверждение о предложенном тексте; отдельного отказа нет. Skip не создаёт утверждений. Точное совпадение текста исправления переиспользует вариант; лингвистическая нормализация и объединение синонимов не реализованы. Сервер сохраняет автора, момент отправки и неизменный снимок доверия. Повтор сдачи не создаёт ответа; другая нагрузка для той же выдачи даёт 409.

Статистика считает последнее принятие человека по случаю целиком: 85 за A и 15 за B = 85%/15%. Skip не стирает принятие; прежние отправки сохраняются. При нуле принятий supportRatio=null. Кандидату нужны собственные N независимых определённых показов и охват; автор собственного исправления не входит в независимую выборку. Новые кандидаты показываются по одному по очереди. Небольшая новая выборка не отменяет ещё подходящее большинство старого варианта.

Фоновый обработчик Outbox рассчитывает текущую редакцию согласования и доверие одной транзакцией; чтение статистики не ждёт фонового расчёта и показывает сами принятия. Решение сообщества не закрывает проверку. При потере определённого результата создаётся Pending, но прежние вклады доверия сохраняются до нового определённого решения. Непринятые варианты автоматически ошибочными не становятся.

Эксперт читает очередь/историю, может добавить собственный текст, выбрать один основной и до четырёх дополнительных допустимых переводов, явно указать неверные. Ожидаемая ревизия защищает от перезаписи старого решения. После закрытия новые ответы по ранее выданным заданиям архивируются без изменения результата/доверия. Основной и дополнительный допустимые варианты одинаково корректны для доверия и учебного ключа.

TrustAssessment хранит историю, TrustContribution — текущий вклад. Повтор события не удваивает вклад, новый ответ оценивается и без смены результата, позднее сообщение читает текущую редакцию. Если A и предложенный B неверны, за ответ с B начисляется одна ошибка. Обновления счётчиков выполняются дельтами. Скрытое доверие не выдаётся в DTO ученика/учителя/экспорта.

Экспорт использует исходные имена колонок, confirmed — целое число людей, принявших основной вариант; status — confirmed/expert_review. Проверяются глобальные/собственные поставщицкие/case-области, включая пагинацию; чтение фиксирует снимок БД.

Добавлены списки доступных школ/классов/учеников и управление фиксированными назначениями. Сессии имеют непрозрачный refresh-секрет на 30 дней с ротацией; в БД только его SHA-256. Повтор старого refresh отзывает семейство сессии. Refresh передаётся явно JSON-полем, не в JWT/URL/cookie. Пользователь может завершить свою сессию и сменить свой пароль с проверкой прежнего; смена пароля отзывает access и refresh.

Базовый дневной урок содержит до 10 переводных заданий из принятых редакций, дата по Learning:TimeZone (по умолчанию Europe/Moscow), размер — Learning:LessonSize. Повтор получения возвращает тот же урок. Упражнение сохраняет закрытый ключ со всеми допустимыми текстами своей редакции. Recognized=true означает точное совпадение с ним, false — неизвестную ключу формулировку, не лингвистический вердикт. Сдача повторобезопасна, чужой участник её не сдаёт, обычная попытка не создаёт голос и не меняет доверие. Баллы и игровые механики не добавлены.

В PostgreSQL записи используют Serializable и транзакционные advisory-блокировки; экспорт — RepeatableRead. Конфликт сериализации/уникальности, в том числе обёрнутый исключением провайдера, возвращает 409. Клиент повторяет исходный запрос; фоновые задачи остаются на повтор. Проверены параллельные случаи одного участника с повторным пересчётом на PostgreSQL.

## Запуск

Один образ API из корневого `Dockerfile`; Compose и Aspire в проекте отсутствуют по последнему указанию пользователя. PostgreSQL запускается отдельно и задаётся строкой подключения. Dockerfile собирает Release-publish и запускает API непривилегированным пользователем на порту 8080.

Настройки передаются обычной конфигурацией ASP.NET Core: appsettings.json/appsettings.Production.json, переменными окружения или секретами платформы, предоставленными как переменные окружения. Исходники/образ для разных серверов не меняются. Минимальный `.env` на сервере, вне Git:

```dotenv
ConnectionStrings__Core=Host=db;Port=5432;Database=bashkir_school;Username=school;Password=<пароль БД>
Jwt__SigningKey=<постоянный случайный секрет минимум 32 байта UTF-8>
Bootstrap__Username=admin
Bootstrap__Password=<сильный первоначальный пароль>
```

Issuer/audience имеют значения `BashkirSchool.Core`/`BashkirSchool.Clients` из appsettings.json и при необходимости переопределяются через Jwt__Issuer/Jwt__Audience. Строка подключения содержит адрес PostgreSQL, доступный из контейнера. На первом запуске нужны bootstrap-секреты; на последующих они не требуются и не меняют существующие аккаунты/пароли.

```sh
docker build -t bashkir-school-core .
docker run -d --name bashkir-school-core --restart unless-stopped --env-file .env -p 8080:8080 bashkir-school-core
```

При обычном старте API проверяет обязательную конфигурацию, выполняет `Database.MigrateAsync()`, затем создаёт первого администратора и начальные настройки, если аккаунтов ещё нет. До окончания этих операций HTTP-сервер не принимает запросы. При ошибке подключения/миграции или отсутствии bootstrap-секретов на пустой базе процесс завершается с ошибкой. У пользователя PostgreSQL должны быть права применять миграции к целевой базе. На обновлении образа применяются только новые миграции.

Bootstrap между одновременно запускаемыми экземплярами защищён advisory-блокировкой; миграции используют собственную блокировку EF Core. Старые режимы `--migrate`/`--bootstrap-admin` сохранены как необязательные служебные команды. Вручную применять SQL или запускать отдельную миграционную команду для обычного развёртывания не нужно; SQL-дубль удалён.

По умолчанию Data Protection хранит ключи в таблице `DataProtectionKeys` этой же БД. Ключи JWT задаются постоянным секретом конфигурации. Контейнеру не нужен отдельный volume для ключей; замена контейнера сохраняет возможность проверки ссылок. Необязательный DataProtection__KeyDirectory оставлен для явного выбора файлового хранилища; только в таком режиме на Windows применяется DPAPI. За внешний HTTPS отвечает настроенный reverse proxy или HTTPS endpoint.

`/health/live` проверяет процесс; `/health/ready` — соединение с БД, но не соответствие схемы миграциям. OpenAPI доступен в Development по `/openapi/v1.json`; сохранённый документ — [docs/openapi.json](docs/openapi.json), запросы внешним командам — `src/BashkirSchool.Host/core.http`. Telegram, браузерный интерфейс и игровые механики в ядро не добавлены. Браузерный cookie-протокол refresh отдельно не фиксировался.

## Проверка и пределы результата

```powershell
dotnet build BashkirSchool.slnx
dotnet test BashkirSchool.slnx --logger 'trx;LogFileName=core.trx' --results-directory TestResults
```

Тесты включают реальный PostgreSQL 18.7 и параллельные операции. Полная матрица и итоговые счётчики — [docs/VERIFICATION.md](docs/VERIFICATION.md). SQLite-фабрика явно отключает автоматическую инициализацию и фоновый обработчик для детерминированных проверок; обычный серверный запуск включает их по умолчанию. Исторические тесты отказов заменены тестами последних принятий согласно прямому уточнению пользователя.

HTTP-тесты запускают настоящий ASP.NET Core pipeline, Identity, Data Protection и JWT, но используют SQLite как реляционный тестовый адаптер. Отдельно проверяется генерируемая PostgreSQL-схема. Для PostgreSQL-тестов задаётся `BASHKIR_TEST_POSTGRES` — подключение к тестовому серверу с правом CREATE DATABASE. Каждый тест создаёт и удаляет только свою отдельную базу с генерируемым именем, не изменяя базу из строки подключения. Проверяются миграции пустой БД, bootstrap, повторный запуск без сброса паролей и работа прежней ссылки после перезапуска.

Для проверки скачан официальный переносимый PostgreSQL 18.7: архив в игнорируемой .data/postgres-runtime, исполняемые файлы/кластер — во временном ASCII-каталоге из-за ошибки кодировки PostgreSQL в кириллическом пути. Служба и Docker не устанавливались. Тесты запускают отдельные временные базы; процесс PostgreSQL останавливается после проверки. Docker Engine отсутствует, поэтому именно сборка Docker-образа не выполнена; Release-publish выполнен той же командой, что в Dockerfile.

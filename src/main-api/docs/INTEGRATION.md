# Подключение ядра в общем репозитории

14 ноября 2026. Каталог ядра — `src/main-api`. Контракт HTTP — [openapi.json](openapi.json), примеры — [core.http](../src/BashkirSchool.Host/core.http). Правила продукта определяются [START-HERE.md](../START-HERE.md).

## Запуск и секреты

Ядро поставляется одним Dockerfile. Существующий корневой `compose.yaml` собирает его с контекстом `./src/main-api`. Отдельные Compose или Aspire для ядра не нужны.

В корневой `.env` или секретах Coolify задайте:

| Переменная общего проекта | Конфигурация ядра | Значение |
| --- | --- | --- |
| `POSTGRES_PASSWORD` | пароль в `ConnectionStrings__Core` | Пароль PostgreSQL |
| `JWT_SIGNING_KEY` | `Jwt__SigningKey` | Постоянный случайный секрет не короче 32 байт UTF-8 |
| `BOOTSTRAP_USERNAME` | `Bootstrap__Username` | Первый администратор, по умолчанию `admin` |
| `BOOTSTRAP_PASSWORD` | `Bootstrap__Password` | Минимум 12 символов, строчные/прописные буквы, цифра и специальный символ |

`INTERNAL_API_KEY` остаётся настройкой прежнего бота; ядро и LMS его не используют. Строка подключения ядра называется `Core`, не `Default`; Compose направляет её на `Host=core-db;Database=core;Username=app`. Issuer/audience по умолчанию: `BashkirSchool.Core` / `BashkirSchool.Clients`.

Автономный запуск описан в [IMPLEMENTATION.md](../IMPLEMENTATION.md). `.env` не загружается приложением автоматически: значения должен передать Docker или среда запуска. Примеры секретов из `.env.example` перед использованием замените случайными значениями.

Ядро применяет миграции до открытия HTTP-порта, создаёт первого администратора только на базе без аккаунтов и хранит Data Protection в PostgreSQL. Bootstrap-пароль не сбрасывает существующего администратора. Корневой Compose требует эту переменную даже после первого запуска. JWT-секрет сохраняйте между обновлениями.

## Сохранность прежней базы

Прежний main-api использовал таблицы `app_users`, `submissions`, `point_events`, `translations`. У ядра собственные Identity/доменные таблицы и история миграций. Автоматического переноса прежних пользователей и ответов нет.

Для core-db выбран новый том `core_data`. Старый `main_data_v2` не удаляется этим изменением и остаётся для отдельного переноса данных. Обновлённый сервис начнёт с новой базы: прежние аккаунты на ней отсутствуют. Прогресс LMS остаётся привязан к прежним ID пользователей. Не подключайте старую базу к ядру без отдельного плана миграции. Не используйте `docker compose down -v` при обновлении с сохранением данных.

## Reverse proxy

Корневой Nginx передаёт пути без переписывания:

| Внешний путь | Назначение |
| --- | --- |
| `/auth/*` | Регистрация, вход, refresh, установка пароля ядра |
| `/api/*` | Защищённое API ядра |
| `/health/live` | Проверка HTTP-процесса ядра |
| `/health/ready` | Проверка соединения ядра с БД |
| `/api/lms/*` | Отдельный LMS API |
| `/api/internal/*` | Закрыт снаружи, 404 |
| `/` | Браузерный клиент |

Healthcheck Nginx проверяет `/health/ready` и `/api/lms/health`. Прежний `/api/health` в новом ядре отсутствует. Проверки подтверждают доступность сервисов и их БД; пользовательские сценарии проверяются отдельно. Оба домена, `bashperevod.ru` и `lms.bashperevod.ru`, направляются на Nginx; каждый клиент обращается к API по собственному origin. Для прямых запросов между отдельными доменами политика CORS пока не настроена.

Nginx передаёт `X-Forwarded-For`, но ядро пока не обрабатывает forwarded headers. Лимит регистрации за прокси применяется по адресу прокси, общему для клиентов. До публичной регистрации настройте доверенные адреса прокси в приложении либо ограничение по клиентскому IP на входном прокси; не включайте безусловное доверие произвольным заголовкам.

## Договор с браузерным клиентом

В коммите `c510a51` клиент `client/src/main.jsx` переведён на новый контракт регистрации, входа и проверки переводов, прежние баллы и рейтинг удалены. Таблица ниже сопоставляет прежние обращения с текущим API:

| Прежнее обращение/ожидание | Контракт ядра |
| --- | --- |
| `/api/auth/register`, поле `displayName` | `POST /auth/register`, только `username`, `password`; ответ — аккаунт, затем отдельный вход |
| `/api/auth/login`, ответ `token` | `POST /auth/sign-in`: `username`, `password`; ответ `accessToken`, `expiresAt`, `refreshToken`, `sessionId`, `refreshExpiresAt` |
| `/api/me`, имя и баллы | `GET /api/me`: `id`, `username`, nullable `schoolId`, `classId` |
| `/api/tasks/today` | `POST /api/reviews/next`: выдача с `id`, `caseId`, `variantId`, `original`, `translation`, `expiresAt`; 204 при отсутствии задания |
| `/api/tasks/{id}/submission`, `answerText` | `POST /api/reviews/{id}/response`: `action` = `Confirm`, `Correct`, `Skip`; для `Correct` поле `correction` |
| `/api/leaderboard`, баллы | Отсутствуют; игровые механики отложены |
| Публичный `/api/translations` | Отсутствует |
| Ссылка на CSV `/api/translations/export` | Защищённый JSON-экспорт с отдельными правами; обычному участнику недоступен |

Все `/api/*` ядра требуют `Authorization: Bearer <accessToken>`. Неизвестные JSON-поля отклоняются. Для refresh используйте `POST /auth/refresh` с `refreshToken`; сохраняйте новый секрет из каждого успешного ответа, старый повторно не используйте. Текущий клиент хранит токены в localStorage отдельно для каждого origin; это поведение клиента, а не обязательное требование API.

Учебный процесс ядра: `GET /api/lessons/today` и `POST /api/exercises/{id}/attempt`; это отдельный контракт от курсов существующего LMS.

## LMS и Telegram

LMS адаптирован в коммите `c510a51`: проверяет JWT через `GET /api/me`, передаёт пользовательский bearer-токен и читает поле `id`; общий внутренний ключ не нужен. Ядро проверяет активность аккаунта и отзыв сессии.

Бот вызывает `/api/internal/telegram/{id}/start`, `/task`, `/me`, `/submit`. Этих маршрутов в ядре нет. Он вынесен в профиль Compose `legacy-bot` и по умолчанию не запускается. Telegram-привязка и пользовательская сессия бота требуют отдельной реализации. Не заменяйте их общим привилегированным ключом, позволяющим выбирать произвольного пользователя.

Прежние JWT, пароли и Telegram-связи автоматически не переносятся. Готовность контейнера ядра не означает готовность прежних клиентов.

## Проверка после развёртывания

1. Проверьте логи main-api: миграции и bootstrap завершились без ошибок.
2. Через внешний адрес проверьте `GET /health/live`, `GET /health/ready`, `GET /api/lms/health`: ожидается 200.
3. Выполните `POST /auth/sign-in` с учётными данными администратора, затем `GET /api/me` с полученным bearer-токеном.
4. Зарегистрируйте отдельного участника через `POST /auth/register`, войдите и проверьте, что у профиля `schoolId` и `classId` равны null.
5. Убедитесь, что `/api/internal/resolve-token` недоступен снаружи (404), а `/api/me` без bearer-токена возвращает 401.

Docker Engine в текущей Windows-среде отсутствует. Сборка образов, `docker compose config`, `nginx -t` и внешний сквозной запуск здесь пока не проверены.

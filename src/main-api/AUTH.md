# Регистрация, вход и привязки: предложение для обсуждения

Самостоятельные участники добавлены: POST /auth/register принимает только username/password, создаёт Account/Participant и собственные наборы account/participant без Enrollment и привилегий. GET /api/me возвращает только свой профиль, реальные schoolId/classId либо null. Публичная регистрация ограничена по видимому серверу IP: 10 запросов за 60 секунд, настройки Registration:PermitLimit/WindowSeconds. За reverse proxy его адрес не подменяется произвольным клиентским заголовком; доверенные прокси требуют серверной конфигурации.

Пользователь выбрал восстановление без школы администратором после ручной проверки. POST /api/accounts/{id}/recovery-link требует accounts.credentials.reset и verificationNote, записываемую в аудит. В примечание нельзя включать пароли или токены. Операция разрешена только обычному самозарегистрированному участнику без зачисления и привилегированных назначений; учитель не получает это право. Переиздание гасит старую ссылку, успешная установка пароля отзывает access/refresh. Сам сервер не заявляет, что автоматически проверил личность: основание проверки предоставляет администратор.

Текущее состояние после реализации школьного MVP: дополнительно проверяется SessionId в JWT; непрозрачный refresh на 30 дней вращается при каждом использовании, в БД хранится только SHA-256. Повтор использованного refresh отзывает эту сессию. Собственные сессии можно завершить; смена своего пароля проверяет старый пароль и отзывает access/refresh. Текущий refresh передаётся явно JSON-телом, не cookie; изложенные ниже cookie-варианты остаются будущим протоколом, а не фактическим поведением. Ключи Data Protection по умолчанию находятся в PostgreSQL и переживают замену контейнера.

Актуализация 14 ноября 2026: в ходе реализации пользователь подтвердил собственную выдачу JWT ядром на 15 минут, проверку состояния аккаунта при запросе, ссылки установки/сброса на 24 часа, отмену старой ссылки при повторной выдаче и отзыв сессий при смене пароля. Администратор создаёт школы и назначает учителей/экспертов; учителя создают классы и учеников. Эти решения имеют приоритет над сохранёнными ниже альтернативами. Реализация и оставшиеся границы — [IMPLEMENTATION.md](IMPLEMENTATION.md).

Зафиксировано пользователем: учитель создаёт учеников, ученик входит по логину и паролю без обязательного email/Telegram, учитель может сбросить пароль. Telegram — дополнительный канал. JWT — выбранное направление доступа к API; механизм выдачи ещё выбирается. Сайт понимается как браузерный клиент нашего API без отдельного веб-бэкенда; домены и развёртывание нужно подтвердить с фронтендом.

Зафиксировано: авторизация по конкретным правам и области действия, не по названиям ролей. Внутренние роли — наборы прав в БД, без обязательного публичного интерфейса управления. Каталог и стартовые наборы: [PERMISSIONS.md](PERMISSIONS.md).

## 0. Выбранный школьный сценарий и предлагаемые детали

1. Учитель создаёт конкретного ученика в доступном ему классе. Ядро создаёт Account, Participant и Enrollment. Повтор запроса не создаёт второго ученика.
2. Предлагается выдать уникальный логин и одноразовый начальный секрет. Учитель передаёт их ученику; постоянный пароль позже недоступен учителю. В БД сохраняются криптографические хеши, а не читаемые пароли.
3. Предлагается при первом входе разрешать только установку собственного пароля. Ограничение проверяется сервером, не только интерфейсом; до смены секрета полный доступ к заданиям не выдаётся.
4. Ученик затем входит по логину/паролю. Email и Telegram не обязательны.
5. Учитель может сбросить пароль только ученику своего класса. Предлагается новый одноразовый секрет с обязательной сменой, отзыв прежних сессий и запись действия в аудит без самого секрета.
6. Смена пароля не делает уже подписанные JWT недействительными сама по себе. Для немедленного отзыва предлагается проверяемая сервером версия доступа/сессии, наряду с отзывом refresh credentials.
7. Telegram по умолчанию привязывается к существующему школьному аккаунту, сохраняя ParticipantId. Самостоятельная регистрация через бота возможна отдельно; автоматического слияния по имени нет.

Сброс позволяет восстановить доступ к аккаунту ученика и потенциально даёт учителю временный доступ; это сознательная ответственность роли, требующая проверки класса, аудита и недавнего подтверждения входа учителем. Он не раскрывает старый пароль и не удаляет/переносит Telegram-привязку автоматически.

Для браузерного клиента предлагаются access token в памяти страницы и обновление через Secure HttpOnly cookie ядра. Для cookie-операций нужна защита от CSRF; разрешённые CORS origins задаются явно. SameSite и доступность cookie зависят от доменов; предпочтительно фронтенд и API в одной site. Это ещё предложение, а не утверждённый протокол.

Основные фичи: CreateStudentAccount, CompleteInitialPasswordSetup, SignIn, RefreshSession, RevokeSession, TeacherResetStudentPassword, RequestAccountLink, ConfirmAccountLink. Дополнительные записи: StudentCredentialSetup и PasswordResetAudit.

## 1. Четыре разных процесса

### Обсуждаемая альтернатива: ссылка вместо временного пароля

Пользователь предложил выдавать персональную временную ссылку как для первичной установки, так и для восстановления пароля, без хранения самой ссылки. Это может заменить временный пароль из раздела 0; окончательный выбор ещё обсуждается.

Предлагаемый процесс: учитель создаёт ученика или запрашивает восстановление → ядро генерирует защищённый ограниченный по времени токен → учитель передаёт ссылку → ученик открывает форму и отправляет новый пароль → ядро проверяет токен и атомарно обновляет пароль и состояние безопасности → ученик входит обычным способом.

Хранить отдельную строку токена не обязательно. Стандартный Identity DataProtectorTokenProvider связывает токен с пользователем, назначением, временем и SecurityStamp. Смена состояния безопасности после успешной операции делает прежние токены недействительными. Полностью бессостоянийный подписанный токен без проверки изменяемого состояния допускает повторное использование до истечения срока.

Ссылка только открывает форму; GET не меняет пароль и не погашает токен. Успешный POST завершает операцию, конкурентные попытки проверяются. Повторная выдача ссылки сама по себе не обязательно отменяет предыдущую — если требуется «работает только последняя», нужен явно обновляемый счётчик/штамп. Для ASP.NET Core Data Protection ключи сохраняются вне временной памяти процесса и доступны всем экземплярам ядра.

В ссылке токен только для установки пароля, не access/refresh JWT и не полноценный вход. Его не пишут в аудит, стороннюю аналитику и журналы URL; страница не должна передавать секрет внешним ресурсам. Стандартный защищённый токен может быть длиннее Telegram start (64 символа): для прямой start-привязки нужен отдельный короткий код/контекст, а не этот же механизм без изменений.

- Регистрация: создать Account и связанного Participant.
- Аутентификация: доказать владение учётной записью и открыть сессию.
- Привязка: добавить способ входа к существующему Account, сохранив ParticipantId, голоса и прогресс.
- Зачисление: присоединить участника к классу по полномочиям учителя/приглашению. Не обязательно создаёт новый аккаунт.

Account — доступ и состояние блокировки; Participant — предметный профиль. Одному Account соответствует один Participant в предложении MVP. ExternalLogin(provider, providerSubjectId) уникален и указывает на Account. Telegram username не идентификатор входа: используется Telegram user ID, полученный доверенным ботом из Update.

## 2. Роль JWT

JWT access token применяется для обращений к ядру после входа. Ядро проверяет подпись, issuer, audience, срок и необходимые права. В токен не входят скрытое доверие, пароль или ключи ответов. Сессионная и авторизационная модель не сводится к подписи JWT.

Предлагаются короткоживущие access tokens, обновляемые сессии с ротацией refresh credentials и серверной возможностью отзыва. Точные сроки не утверждены. При блокировке и изменении роли нужна явная политика действия уже выданных токенов; минимальный вариант — короткий срок, для немедленного запрета проверка состояния/версии доступа.

Для C# можно использовать ASP.NET Core Identity для аккаунтов, паролей, ролей и стандартных операций подтверждения/восстановления. Это не готовый OAuth/OIDC issuer. Для стандартной выдачи JWT выбирается отдельный поддерживаемый механизм, например OpenIddict либо внешний поставщик. Не считать встроенные Identity bearer tokens автоматически JWT.

Для сайта с собственным сервером предпочтительно хранить access/refresh на его сервере и давать браузеру защищённую HttpOnly cookie с защитой от CSRF. Если сайт — только SPA, схема входа, обновления и хранения выбирается с фронтендом отдельно; не фиксировать localStorage как решение по умолчанию.

## 3. Самостоятельная регистрация в Telegram

1. Пользователь пишет боту /start; бот получает Telegram user ID из настоящего обновления.
2. Бот по защищённому интерфейсу сообщает ядру о пользователе. Ядро доверяет этой аттестации только специальному зарегистрированному бот-клиенту, не произвольному HTTP-вызову.
3. Если привязка уже есть — открывается пользовательская сессия соответствующего Account. Если нет — бот предлагает создать аккаунт либо связать существующий.
4. Для нового аккаунта создаётся Participant, запрашивается нужный профиль; школьная принадлежность подтверждается отдельным приглашением/процессом.

Обычный /start сам по себе не требует секретной ссылки для регистрации нового пользователя. Специальная ссылка нужна для контекста приглашения или связывания. Бот хранит пользовательские токены на своей стороне, не отправляет их в чат. Способ получения делегированной сессии согласуется с выбранным issuer; произвольный client credentials токен не равен пользовательскому.

## 4. Привязка Telegram к веб-аккаунту

Предлагаемая схема:

1. Уже вошедший пользователь на сайте запрашивает привязку.
2. Ядро создаёт AccountLinkRequest с purpose, AccountId, сроком и случайным одноразовым кодом. В БД хранится хеш секрета.
3. Сайт показывает `https://t.me/OurBot?start=link_<opaque-code>`.
4. Бот получает код и Telegram user ID, передаёт их ядру через свой защищённый интерфейс.
5. Сайт в исходной авторизованной сессии показывает найденную Telegram-идентичность и просит подтвердить привязку. Бот также явно показывает действие; при необходимости используется сверяемый код.
6. После подтверждений ядро атомарно создаёт ExternalLogin и погашает запрос. ID Telegram, уже привязанный к другому аккаунту, не переносится автоматически.

Один клик по пересланной ссылке не должен незаметно связать чужие аккаунты. Инициатор привязки и бот подтверждают намерение. Полный JWT и refresh token не передаются в start, URL или чат. Telegram ограничивает параметр start 64 символами; используется короткий base64url-совместимый непрозрачный код.

Обратное направление: в боте запросить переход на сайт → одноразовый контекст входа → независимая браузерная сессия подтверждает действие → пользователь завершает вход/настройку веб-способа. Нельзя одной публичной ссылкой одновременно подтверждать чужую веб-сессию без привязки к инициатору. Детальный протокол зависит от выбранного входа и issuer.

## 5. Учитель и класс

Вариант A: учитель создаёт приглашение в свой класс. Новый ученик регистрируется через сайт/бота и погашает приглашение; существующий входит в свой аккаунт и присоединяется без нового Account. Код класса даёт право запросить зачисление, не получить доступ к чужому аккаунту. Общая ссылка может пересылаться, поэтому нужны подтверждение учителем или ограничения использования.

Вариант B: учитель создаёт список учащихся с ещё не активированными школьными профилями и отдельными одноразовыми приглашениями. Ученик подтверждённо получает свой код и активирует профиль либо связывает его с существующим аккаунтом. До подтверждения принадлежности нельзя присваивать чужую историю. Реализация сложнее, но ближе к буквальному «учитель регистрирует ученика».

Вариант C: учитель создаёт временные логины/пароли. Требуются доставка, смена пароля и восстановление; роль учителя не должна позволять читать постоянные пароли или входить за ученика. Для MVP не предлагается первым вариантом.

Эти варианты сохранены для сравнения: основным теперь выбран сценарий предварительного создания конкретных учеников с логином/паролем из раздела 0. Общая ссылка класса не заменяет его. Роль учителя не выдаётся при саморегистрации.

## 6. Минимальные классы

Account, ExternalLogin, Session, AccountLinkRequest, ClassInvitation, Enrollment. Резерв учащегося добавляется только при выборе варианта B. Одноразовые записи назначения Register/Link/Enroll/Login не взаимозаменяемы.

Фичи: RegisterAccount, SignIn, RefreshSession, RevokeSession, RequestAccountLink, ConfirmAccountLink, CreateClassInvitation, RedeemClassInvitation. Реальные HTTP-маршруты и стандартизованные протоколы ещё не проектировались.

Не объединять аккаунты по одинаковому имени/email из непроверенного профиля. Для пользователей, независимо зарегистрировавшихся в вебе и Telegram, нужен отдельный защищённый сценарий разрешения дубля; автоматическое слияние голосов и прогресса не согласовано.

## 7. Вопросы перед выбором

1. Кто создаёт/подтверждает учителей и школы? Предложение: администратор.
2. Нужна ли открытая веб-регистрация уже в MVP и как пользователь без учителя восстанавливает доступ без email/Telegram? Исходное ТЗ допускает самостоятельную регистрацию, требование пока не отменено.
3. Подтверждается ли обязательная смена начального/сброшенного секрета? Сейчас это предложение.
4. Какие домены будут у фронтенда/API и какой механизм стандартной выдачи JWT выбираем?

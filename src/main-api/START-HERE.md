## 2. Зафиксированный объём

- C# / ASP.NET Core, PostgreSQL, одно приложение с логическими модулями.
- Веб — отдельный браузерный клиент. Telegram-бот и подготовка материалов принадлежат другим участникам. Все обращаются к HTTP API ядра.
- В ядре нет парсинга документов, распознавания/нарезки аудио, Telegram webhook/FSM, интерфейсов чужих приложений.
- Ядро принимает готовые оригиналы, машинные переводы и координаты источника; управляет пользователями, выдачами, ответами, согласованием, экспертизой, доверием, учебными заданиями и экспортом.
- Игровая экономика, баллы, достижения и сравнение игровых рейтингов **отложены**. Не реализовывать выдуманные правила ради заполнения классов.
- Яндекс — только отдельные слова, не переводы предложений. Владелец интеграции и языковая поддержка ещё не проверены; интеграция не нужна для первого сквозного процесса.

## 3. Главный процесс первой версии

1. Поставка создаёт Fragment и TranslationCase для языковой пары, сохраняет машинный кандидат и источник.
2. Распределитель выбирает случай с учётом охвата школ/классов, истории и незавершённых выдач.
3. Первая реализуемая форма — **один показанный перевод**, подтвердить либо отклонить с исправлением. «Не знаю» — возможность пропуска без участия в проценте.
4. ReviewAssignment фиксирует, что действительно было показано. Сервер назначает автора, доверие на момент отправки и контекст дня/пачки.
5. ReviewResponse сохраняет отправку и её отдельные VariantJudgment. Новая допустимая выдача в другой день/пачке позволяет тому же человеку ответить вновь. Повтор запроса одной выдачи не создаёт нового ответа.
6. Последнее уточнение пользователя: учитываются только принятия, отдельных отказов нет. Поддержка варианта — число уникальных участников, последнее принятие которых относится к нему, делённое на число участников с любым принятием по случаю. 85 за A и 15 за B = 85%/15%. При нуле принятий процент отсутствует.
7. Голоса привязаны к тексту/VariantId: подтверждение старого перевода не становится подтверждением нового. История предложения общая, статистика показываемой формулировки не смешивается с историей других формулировок.
8. После достаточного числа оценок и требуемого охвата поддержка не ниже порога (рабочее значение 80%) разрешает принять один основной вариант сообществом. Недостаточное согласие отправляет случай эксперту.
9. Согласование постоянно активно до решения эксперта. Принятие сообществом разрешает использовать перевод в большем числе упражнений, но не закрывает проверку.
10. Эксперт видит спорные случаи с наиболее спорными сверху, может выбрать любой доступный, установить один основной и до четырёх дополнительных допустимых переводов, закрыть случай.
11. После экспертного решения новые замечания только сохраняются, не меняют консенсус/доверие и не запускают переоткрытие.

Для большинства действует последнее принятие участника по случаю целиком. Confirm поддерживает показанный текст; Correct поддерживает только предложенный текст; Skip не стирает принятие. Все допустимые исторические отправки сохраняются для доверия. Вес доверия в голосах не используется. Новым кандидатам нужна собственная независимая выборка, автор своего исправления в неё не входит. В неопределённом состоянии остаётся один показанный перевод, не множественный выбор.

## 4. Доверие

- Формула: `(correct + 5) / (total + 10)`, новичок 0,5.
- После появления принятого результата оцениваются утверждения; при изменении допустимости они переоцениваются. Новые ответы оцениваются и без смены результата.
- Итоговые счётчики обновляются как старые − прежний вклад + новый. История не забывается и не начисляется повторно.
- Историческое доверие при отправке неизменно. Одновременные операции и старые события не теряют/не откатывают обновления.
- Если эксперт признал старую формулировку дополнительной допустимой, её выбор правильный, даже если она не основная.
- В расширенном множественном выборе каждый выбранный вариант — отдельная оценка: выбранные 1,3,4 при допустимых 1,2 и неверных 3,4 дают correct +1 / total +3. Это согласованный смысл модели, **но интерфейс множественного выбора не нужен в первой версии**.
- Обычная учебная попытка сама по себе не меняет доверие. Отдельное оспаривание до эксперта входит в общий процесс; не создавать двойной голос из попытки и кнопки ошибки.
- Ещё не рассмотренный перевод не равен доказанно неверному. Не применять правило «не лидер = ошибка» без согласования.
- Уточнено пользователем: исправление даёт один вклад за предложенный текст, без бонуса за отклонение исходного. Если определённый результат утрачен, прежние вклады доверия сохраняются до нового определённого решения. Отдельные отказы не создаются и не оцениваются.

## 5. Распределение и настройки

Контролируем предложение/TranslationCase, а не отдельный тип задания. Несколько типов и пачек могут собирать данные для него. Сосредоточиваем выдачу на рабочем наборе случаев, чтобы постепенно получать достаточные выборки.

Подбор учитывает недопредставленные школы, затем классы, затем повторы; резервирования учитываются до получения ответа. Случайность допустима только при равных приоритетах; шум Перлина не нужен.

Административные настройки версионируются: N, порог согласия, минимальный охват школ/классов, максимальные доли групп, ограничения повторов, размер рабочего набора, сроки выдач. Цифры 2 школы / 3 класса / 60% / 40% были примерами, не обязательными бизнес-константами. Проверять совместимость настроек и режим нехватки аудитории.

## 6. Аккаунты и права

- Учитель создаёт конкретных учеников своих классов. Вход ученика — логин/пароль без обязательных email/Telegram. Учитель может восстановить доступ только своему ученику.
- Самостоятельный участник регистрируется по логину/паролю без школы, email и Telegram. Его принятия входят в общий N и процент; школьный охват сохраняется. Восстановление — администратором после ручной проверки, с отдельным правом accounts.credentials.reset и причиной в аудите. Этот путь не разрешает сбрасывать школьные или привилегированные аккаунты.
- Последнее обсуждённое направление — персональная временная ссылка для первичной установки и восстановления пароля, без хранения каждой ссылки в отдельной строке БД. Это ссылка только для установки пароля, не полноценный access JWT. Сам аккаунт и изменяемое состояние безопасности хранятся; успешная установка делает прежний токен недействительным. Срок, повторная выдача и отзыв сессий требуют явно выбранной политики.
- Предпочтительны стандартные средства ASP.NET Core Identity/Data Protection, а не самодельная криптография. Ключи сохраняются между перезапусками; безопасность JWT-сессий не отзывается одной сменой SecurityStamp автоматически.
- Согласовано при реализации: ядро выдаёт JWT на 15 минут, issuer/audience и ключ задаются конфигурацией. Каждый запрос проверяет активность и SessionVersion. Ссылка установки/сброса действует 24 часа; повторная выдача отменяет предыдущую; смена пароля отзывает все JWT. Identity bearer token не используется вместо JWT.
- Администратор добавляет школы и назначает учителей/экспертов; учителя создают классы в своих школах и учеников своих классов.
- Telegram дополнительно привязывается к тому же аккаунту; самостоятельная регистрация возможна. Не создавать/сливать пользователей по совпадению имени.
- Авторизация — permissions + область конкретного ресурса. Внутренние роли лишь наборы прав в БД, не IsInRole/Authorize(Roles). Публичный редактор ролей не нужен.
- Стартовые наборы: участник, учитель, эксперт, администратор, поставщик данных, бот-приложение, потребитель экспорта. Каталог в PERMISSIONS.md. Администратор не автоматически эксперт; секрет бота не даёт права действовать за произвольного ученика.

## 7. Данные и техническая простота

Минимальная поставка близка к ТЗ: fragment_id, text_ba, lang_pair, translation (машинный кандидат), source. ProducerId определяется аутентификацией, пакет идемпотентен. Экспорт — таблица исходного ТЗ; не проектировать внутреннюю БД как эту плоскую таблицу.

Сохранять историю вариантов, выдач, утверждений, редакций результата, оценок и политики. Индексы/ограничения предотвращают дубли. Транзакции защищают ответ, идемпотентный результат и сообщение пересчёта. Outbox/таблица задач достаточны; Redis, Kafka, микросервисы и универсальная платформа плагинов не нужны.

## 8. Что ещё действительно не закрыто

Это небольшой список перед реализацией конкретных ветвей, не повод заново обсуждать весь продукт:

1. **Смена кандидата:** реализован показ по одному с приоритетом меньшей выборки; N и охват проверяются отдельно у кандидата. Малое число новых принятий само по себе не снимает старое принятие, пока оно удовлетворяет правилам.
2. **Оценка доверия:** пользователь утвердил один вклад за предложенный текст. Если A и предложенный B неверны, за отправку с B одна ошибка, без второго вклада за A.
3. **Потеря определённости:** пользователь утвердил сохранение прежних вкладов до нового определённого решения.
4. **Неправильность вариантов:** автоматика не объявляет проигравшие варианты неверными. Эксперт явно указывает неверные; нерассмотренные остаются неопределёнными.
5. **Начальные значения:** по указанию пользователя реализованы изменяемые администратором версии настроек. Старт: N=100, порог 80%, минимум 2 школы/3 класса, доли 60%/40%, выдача 30 минут, повтор через 24 часа, рабочий набор 20. При нехватке аудитории квоты не ослабляются автоматически. Участники без школы работают в общем потоке, но не увеличивают школьный охват и не разбавляют школьные доли групп.
6. **Развёртывание/вход:** выбраны .NET 10 и собственная выдача JWT ядром, сроки и отзыв описаны в разделе 6. Учителей/экспертов назначает администратор. Восстановление самостоятельного аккаунта — административное; домены клиента/API остаются открытыми.

Все остальные будущие игровые и эксплуатационные вопросы в QUESTIONS.md. Они не блокируют импорт, сущности, permissions и каркас проверки. Блокеры алгоритмов не обходить возвратом фиктивных результатов.

## 9. Порядок следующей реализации

Окружение: .NET SDK 10.0.404, ASP.NET Core 10.0.15, Git и NuGet. Развёртывание — один Dockerfile, без Compose/Aspire; миграции и bootstrap выполняются обычным запуском, ключи восстановления хранятся в PostgreSQL. Для проверок подключён переносимый PostgreSQL 18.7 без службы, проверены реальная миграция, обновление старой базы, фоновый и параллельный пересчёт. Docker Engine не установлен: именно Docker build ещё не выполнялся. Действующие правила — CONSENSUS.md, состояние и запуск — [IMPLEMENTATION.md](IMPLEMENTATION.md). Пункты плана ниже реализованы в школьном MVP; дальнейшие ветви — QUESTIONS.md.

1. Проверить .NET SDK, Git, инструкции проекта, доступ к пакетам и PostgreSQL. Закрепить поддерживаемую версию SDK и пакетов; не создавать игровой фронтенд.
2. Создать Domain, Application, Infrastructure, Host и проект значимых тестов. Проверить граф зависимостей; не создавать пустые интерфейсы для каждой сущности.
3. Описать сущности/ограничения PostgreSQL, миграцию и минимальные начальные наборы permissions. Создание первого администратора — отдельный контролируемый bootstrap.
4. Реализовать идентичность/permissions и один школьный сценарий: учитель → ученик → ссылка установки пароля → вход → доступ только к своим ресурсам. Точный issuer согласовать перед выдачей JWT.
5. Реализовать сквозной процесс: поставка → случай → распределение/выдача → подтверждение/исправление → сохранение → статистика. Подготовить OpenAPI и запросы .http для внешних команд.
6. После уточнения пунктов 1–4 раздела 8 реализовать смену результата, оценку доверия, экспертное закрытие и экспорт. Для проверки порогов использовать небольшие тестовые настройки, а не менять продакшен-правило.
7. Только затем добавлять уроки/игры и отдельно согласовывать их экономику.

## 10. Значимые проверки первого сквозного процесса

- 85 принятий A / 15 принятий B = 85%/15%; 0 принятий — неопределённый процент; границы N и 80% включительны.
- Повтор той же отправки не дублирует голос; новая допустимая выдача сохраняется, но не создаёт нового уникального человека.
- Голоса A не подтверждают B; отклонение A не поддерживает автоматически одно и то же исправление всех авторов.
- Принятый сообществом случай остаётся активным; экспертное решение не затирается поздним пересчётом.
- Обновление оценки меняет только прежний вклад; повтор события и параллельные случаи не искажают TrustProfile.
- Ученик не видит доверие/ключи; учитель не восстанавливает доступ чужому классу; сайт не использует сервисные секреты бота.
- Резервирования предотвращают массовую концентрацию выдач в одном классе; истечение освобождает место.
- Смена основного текста не делает допустимый синоним ошибочным; архивное замечание после эксперта не меняет итог.

Это план тестов, не заявление об уже пройденных проверках.

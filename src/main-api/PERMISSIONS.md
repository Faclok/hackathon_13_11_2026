# Авторизация по правам

Реализация школьного MVP: базовый внутренний набор `account` выдаёт только собственные profile.read/sessions.manage/credentials.change и назначается каждому аккаунту. Учебный набор добавляет lessons.receive/exercises.submit. Учитель создаёт и видит свои классы назначенной школы; администратор читает системные списки через schools.manage/classes.manage/enrollments.manage. Эксперту и потребителю экспорта можно назначить глобальную или конкретную case-область. Административные операции меняют только фиксированные наборы, не каталог; базовый набор аккаунта и администратора через обычное удаление назначения не отзываются. Фактические DTO не содержат доверия, ключей и внутренних ролей; сведения о назначениях доступны только управляющему доступом администратору.

Зафиксировано пользователем: ASP.NET Core проверяет права, не названия ролей. Роли хранятся внутри БД как наборы прав; публичный конструктор ролей и выдача названий ролей клиентам не требуются. Приведённые ниже стартовые наборы — проектное предложение, не новая функция из исходного ТЗ.

## 1. Правило допуска

Действие разрешено, если субъект аутентифицирован, его доступ активен, имеется конкретное право с подходящей областью действия и выполнены доменные ограничения. Во всех остальных случаях отказ.

Пример: `students.credentials.reset` с областью назначенных классов позволяет учителю выпустить ссылку восстановления ученику своего класса. Наличие этого права не разрешает сбрасывать пароль другим учителям, экспертам или ученикам чужого класса.

Права и границы проверяются как единое назначение. Нельзя взять право из одного назначения, а глобальную область из другого и случайно объединить их в расширенный доступ.

## 2. Хранение — предложение

- **PermissionDefinition**: стабильный код права и описание. Каталог задаётся кодом/миграциями, не произвольным вводом пользователя.
- **AccessProfile**: внутренний набор прав («учитель», «эксперт» и т.д.). Название роли имеет только организационный смысл.
- **AccessProfilePermission**: какие права входят в набор.
- **AccessAssignment**: назначение набора аккаунту или сервисному клиенту с областью и сроком при необходимости.
- **Область**: собственные ресурсы, явно назначенные классы, конкретный поставщик/набор данных, разрешённые направления/случаи либо глобальная.
- **AccessVersion**: ревизия доступа субъекта для отзыва сессий/инвалидации кэша. Общая версия каталога нужна при изменении самого набора, если права кэшируются.

Отдельные прямые разрешения пользователю, запреты, иерархия ролей и граф наследования для MVP не нужны. Все назначения и отзыв аудируются. Нет автоматического правила «администратор обходит все проверки».

## 3. Каталог прав и стартовые наборы

### Участник: ученик или самостоятельный пользователь

Один набор; принадлежность к школе определяется Enrollment, а не отдельной ролью «носитель языка».

| Право | Действие | Область |
|---|---|---|
| profile.read | Читать профиль | Свой |
| profile.update | Изменять разрешённые поля профиля | Свой; без роли, доверия и школьной принадлежности |
| credentials.change | Менять свой пароль | Свой аккаунт, с подтверждением |
| sessions.manage | Завершать свои сессии | Свои |
| identities.link | Подключать/отключать способ входа | Свой аккаунт с подтверждением и сохранением доступного входа |
| reviews.receive | Получать проверочные задания | Свои выдачи по политике распределения |
| reviews.submit | Отправлять мнения | Свои допустимые выдачи |
| translations.challenge | Сообщать об ошибке перевода | Свой показанный контекст |
| lessons.receive | Получать уроки | Свои |
| exercises.submit | Отвечать на упражнения | Свои |
| progress.read | Читать прогресс | Свой |
| leaderboards.read | Читать разрешённые игровые рейтинги | Публичный разрешённый срез без скрытых данных |

### Учитель

Права ниже, а также собственный профиль/пароль/сессии/привязки. Игровой набор не наследуется автоматически; если учитель также участвует, ему назначается и набор участника.

| Право | Действие | Область |
|---|---|---|
| classes.read | Смотреть классы | Назначенные |
| classes.create | Создавать классы | Школа, к которой учителя назначил администратор; созданный класс принадлежит этому учителю |
| students.read | Смотреть учебные профили учеников | Назначенные классы, ограниченные поля |
| students.create | Создавать учеников | Назначенные классы |
| students.credentials.issue | Выпускать ссылку первичной установки пароля | Ученики назначенных классов |
| students.credentials.reset | Выпускать ссылку восстановления | Ученики назначенных классов |
| reports.class.read | Читать учебный отчёт | Назначенные классы |

Учитель не получает чтение паролей, управление чужими сессиями вне восстановления, скрытое доверие, право экспертного решения или произвольную выдачу прав. Перевод между классами и массовое управление зачислением не входят автоматически в students.create.

### Эксперт УФИЦ РАН

Собственный профиль/пароль/сессии/привязки и следующие права:

| Право | Действие | Область |
|---|---|---|
| expert.queue.read | Читать очередь | Разрешённые случаи/направления |
| expert.case.read | Читать материал и доказательства | Разрешённые случаи, без лишних персональных данных |
| expert.translation.resolve | Выбрать основной, допустимые и неверные переводы, закрыть случай | Разрешённый случай с проверкой ревизии |

Эксперт не может произвольно менять доверие числом: оно рассчитывается из оценок. Чтение скрытого доверия не требуется автоматически для вынесения решения и отдельно пока никому из учебных наборов не выдано.

### Администратор ядра

Собственный профиль/пароль/сессии и следующие права:

| Право | Действие | Область |
|---|---|---|
| schools.manage | Управлять школами | Системная |
| classes.manage | Управлять классами | Системная |
| enrollments.manage | Управлять учебной принадлежностью | Системная с историей изменений |
| teachers.manage | Создавать/подтверждать учителей, назначать классы | Системная; требуется подтвердить организационный процесс |
| experts.manage | Создавать аккаунты экспертов и назначать экспертный набор | Системная; подтверждено пользователем при начале реализации |
| accounts.status.manage | Блокировать/разблокировать аккаунты | Системная с аудитом |
| accounts.credentials.reset | Выпустить восстановление самостоятельного аккаунта после ручной проверки | Только самозарегистрированный обычный участник без зачисления/привилегированных назначений; требуется причина в аудите |
| access.assign | Назначать и отзывать утверждённые наборы | Только разрешённые администратору наборы и области |
| policies.consensus.manage | Создавать версии политики согласования | Системная |
| policies.distribution.manage | Настраивать распределение | Системная |
| content.intake.read | Смотреть результат поставок | Системная |
| content.availability.manage | Приостанавливать выдачу дефектного материала | Системная; не подменяет экспертное решение |
| reports.system.read | Читать системную агрегированную статистику | Без скрытого доверия/лишних персональных данных |
| audit.read | Читать журнал действий | Разрешённые события без секретов |

Администратор не автоматически эксперт. Совмещение оформляется явным назначением экспертных прав с областью. Право access.assign не должно позволять выдать права выше своей разрешённой границы, менять каталог или незаметно повысить себя. Первичное назначение администратора — отдельный контролируемый bootstrap при развёртывании.

Для MVP каталог и наборы фиксируются миграциями. Назначение пользователю можно выполнять защищённым административным процессом; отдельный интерфейс редактирования наборов не нужен. Восстановление доступа учителя/администратора пока не определено и не делегируется обычному учителю.

### Сервис подготовки данных

`content.deliver` — передавать готовые фрагменты/переводы только от своего ProducerId; `content.intake.read` — видеть результаты своих поставок. Нет доступа к оценкам учеников, доверию, экспертному решению или таблицам БД.

### Приложение Telegram-бота

`telegram.identity.attest` — подтверждать Telegram-идентичность через специально доверенный договор; `telegram.links.complete` — участвовать в подтверждённой привязке.

Это сервисные возможности, не право читать всех учеников или выполнять любое действие за любого пользователя. Задания и ответы выполняются в подтверждённом пользовательском контексте с правами участника. Способ выдачи такой сессии согласуется с issuer. Секрет бот-клиента не выдаётся браузеру.

### Потребитель переводов: заказчик/LMS

`translations.export` — выгружать разрешённые направления/данные по схеме ТЗ. `reports.class.read` назначается отдельно только если конкретной интеграции действительно нужен отчёт конкретных классов. Нет доступа к ключам игр и скрытому доверию.

### Гость и ограниченная операция по ссылке

Гость не имеет доменных прав; доступны только явно открытые операции входа/регистрации в пределах выбранного сценария. Регистрация не позволяет выбрать привилегии.

Временная ссылка установки пароля не создаёт роль или полноценный JWT. Она разрешает ровно одну целевую операцию для указанного аккаунта после проверки защищённого токена, срока и состояния безопасности. Такие токены не принимаются вместо access token.

## 4. Как проверить в ASP.NET Core

Предложение: фиксированный каталог именованных policies; PermissionRequirement и обработчик вычисляют актуальные grants. `[Authorize(Roles = "Teacher")]`, IsInRole и сравнение названия роли в доменном коде не используются.

Сначала endpoint требует право, затем сценарий/ресурсный authorization handler проверяет принадлежность конкретного ученика/класса/выдачи. Предварительно закрытый UI — удобство, не защита. Право не отменяет доменные условия: экспертно закрытый случай не меняется обычным голосом даже у участника с reviews.submit.

Иллюстрация, не готовый endpoint:

```csharp
// Вход требует право; не название роли.
endpoint.RequireAuthorization("students.credentials.reset");

// После загрузки минимального контекста ресурса:
var access = await authorization.AuthorizeAsync(
    caller, studentAccessContext, "students.credentials.reset");
// Обработчик проверяет: цель — ученик, класс назначен этому учителю,
// назначение права активно и имеет подходящую область.
```

Для защиты от изменений между проверкой и записью чувствительный сценарий проверяет актуальную принадлежность/версию в согласованной транзакции. Во внутренних вызовах сохраняется контекст инициатора; фоновые системные расчёты не становятся публичной возможностью клиента.

## 5. JWT и скрытые роли

Названия AccessProfile не обязательно помещать в JWT или /me. Предложение: JWT содержит идентификаторы субъекта/сессии и необходимые стандартные claims; актуальные права/область ядро получает из БД или контролируемого кэша. При смене назначений кэш инвалидируется; версия доступа проверяется, чтобы не ждать истечения JWT для отзыва.

Подписанный JWT сам по себе не зашифрован: не класть туда секреты, доверие или приватный каталог. Если фронтенду нужен список доступных действий, можно вернуть безопасный набор capabilities без внутренних ролей и назначений. Сервер всё равно проверяет каждый запрос. /me с capabilities не требуется до потребности фронтенда.

## 6. Проверки перед реализацией

- Учитель не сбрасывает пароль ученика чужого класса через подстановку ID.
- Наличие права в одном ограниченном назначении и глобальной области в другом не расширяет первое.
- Удаление назначения и блокировка прекращают доступ согласно политике отзыва, а не только скрывают кнопку.
- Одноразовая ссылка не разрешает менять чужой профиль или выдавать задания.
- Сервисный токен поставщика/бота не принимается как произвольный пользовательский контекст.
- Администратор не назначает себе/другому запрещённый набор через подмену ProfileId/ScopeId.
- Изменение школы/класса меняет текущий доступ, но не переписывает историю охвата.
- Экспорт и отчёты фильтруют строки и поля; пагинация не обходит область доступа.
